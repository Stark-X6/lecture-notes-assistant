# Ticket Lab · 抢票实验室

一个适合软件工程课程展示的本地交互 Demo，包含售票服务、自动抢票程序、模拟手动群众和操作者手动抢票。四者围绕同一批库存交互，可以观察查询与下单的竞争、同人多账号、付款超时、退票回流、候补和服务排队。

## 启动

需要 Node.js 20 或更新版本，无第三方依赖。

- Windows：双击 `start.cmd`，保持窗口运行。
- 命令行：在项目目录运行 `node server.mjs`。
- 浏览器打开 http://127.0.0.1:3186/ 。按 Ctrl+C 停止服务。
- 端口冲突时可设置 `PORT`；启动脚本也会尝试本机已有的 Codex 内置 Node。

## 建议体验顺序

1. 载入练习配置，开始实验。开售后在操作者区域先查询余票，再尝试占票。查询结果有时间戳，并不锁票。
2. 占票成功后，在倒计时结束前确认订单。也可取消占位，观察库存立即释放。
3. 确认后退票，观察票先进入“待回售”，等批次释放后才重新可售。
4. 切换“先售后候补”。售罄后登记候补；有票释放时，服务器按登记生效顺序递补，同一人多账号不增加资格。
5. 比较先到先得、行为防护和窗口抽签，保持其他参数相同。可增加账号数但保持独立购票人数相同，观察刷请求是否等于增加成功机会。
6. 调低服务通道数、提高单次服务时间，观察排队等待。完整轮次保存在最近 10 轮历史中，支持 JSON 导出。

正在运行的轮次须先重置才能换配置；未完成轮次不计入历史。没有给操作者预留票。

## 四种规则

| 模式 | 分配方式 | 观察重点 |
| --- | --- | --- |
| 先到先得 | 业务请求按队列开始处理，实际处理时检查库存 | 反应、网络和服务排队如何共同影响结果 |
| 行为防护 | 在基础流程上，依据账号、购票人、设备的一秒请求窗口慢处理或拒绝 | 程序优势是否降低，正常群众是否也受影响 |
| 窗口抽签 | 窗口内每人一份资格，结束后均匀洗牌；余票按该顺序递补 | 高频提交不增加资格，迟到者可能错过窗口 |
| 先售后候补 | 开始时竞争现票，缺票后按服务器登记生效顺序候补 | 退票、取消和超时如何转给后续购票人 |

服务可有多个通道。入队先后决定开始处理的顺序；慢处理等因素会改变完成时刻，因此不等于严格按客户端点击时间发票。防护规则不会直接读取 crowd / bot / manual 分组来决定资格；分组用于模拟行为和事后统计。没有预设某一方必胜。

## 库存与身份

始终满足：**总票数 = 可售 + 临时占位 + 已确认 + 待回售**。

- 查询只读取当时余票；下单时重新检查。多人都查到一张票，最终仍只能有一人占到。
- 占位后可确认、取消或超时。取消和超时即时释放；候补模式先递补，再让新请求竞争。
- 已确认订单退票进入待回售池，从该批第一张退票开始计时，统一回售。为简化本轮行为，已退票的人不会再次购票。
- 每个群众一个账号和设备；程序账号按“每位购票人账号数”归并，同一人的账号共用一个模拟设备。同一人最多持有一张有效票、一个候补资格。
- 操作者有单独的账号、购票人和设备标识。多个网页标签共用这一身份。

## 指标如何读

| 指标 | 计算口径 |
| --- | --- |
| 最终获票率 | 本组当前有效已确认人数 / 本组独立购票人数，退票后不再计为有效获票 |
| 自动化优势倍数 | 程序获票率 / 群众获票率；无比较组或群众获票率为零时不计算 |
| 每张有效票的请求成本 | claim 提交次数 / 当前有效已确认票数；无有效票时不计算 |
| 防护影响率 | 被慢处理或拒绝过的独立购票人数 / 发起有效业务请求的独立购票人数 |
| 程序拦截率 | 程序组中上述比例，属于行为防护影响指标 |
| 群众误伤比例 | 正常群众中上述比例；只是正常参与者受影响的代理指标，不等同于真实平台分类器的误报率 |
| 付款超时率 | 超时占位次数 / 累计建立占位次数；轮次结束的统一释放不算付款超时 |
| 队列平均等待 | 开始处理时间减去入队时间，按已开始的业务请求统计 |
| 队列 P95 | 队列等待样本的第 95 百分位，最多使用最近 10000 个样本 |
| 平均端到端延迟 | 已完成业务请求从提交到完成的时间，含模拟上行、排队和服务等待 |
| 业务处理耗时 | 实际执行状态更新逻辑的时间，不含上述等待 |

余票查询和购票提交分别计数；网页轮询不计入实验购票请求。确认、取消、退票等进入同一服务队列，但不计入 claim 请求数。导出中的比率包含分子、分母和定义，避免只看百分数。

## 模拟参数与适用边界

默认 30 张票、120 位群众、12 个程序账号；每位程序购票人 2 个账号，实际为 6 位程序购票人。默认共同上行延迟 60ms、波动 40ms；4 个服务通道，每次模拟服务等待 15ms。付款基础等待 850ms、弃付概率 4%、确认后退票概率 10%，首张退票后 3 秒批次回售。这些都是课堂实验设定，**不是现实平台的测量值或内部参数**。

群众在开售后约 300–2500ms 开始，部分人额外迟到；先查询，再经过思考时间提交，失败后最多重试 6 次。程序在开售后约 0–65ms 开始，查询后短暂等待再提交，按配置重试。付款也进入服务队列，拥堵时可能超时。操作者需要亲自确认。

售票端是真实 Node HTTP 服务；群众和程序是后端进程内虚拟参与者，共用同一个业务引擎。不会为每位虚拟用户打开浏览器或创建真实网络连接。服务时间和上行延迟通过定时器模拟，未完整模拟下行、带宽、丢包和互联网拥塞，因此吞吐和延迟不能当作生产系统压测结果。

固定种子控制随机采样，但操作系统调度和真人点击会改变时序，同种子不保证逐次一致。身份假定有效，未实现真实身份核验。数据仅保存在内存，重启会清空；重置保留本进程已完成的最近 10 轮历史。本项目不连接真实票务服务，也不产生真实支付。

现实业务依据与实验步骤分别见 [现实票务机制调研](docs/REAL_WORLD.md) 和 [课堂实验指南](docs/EXPERIMENTS.md)。

## 文件与接口

```text
engine.mjs          实验引擎：身份、队列、库存、参与者、规则和统计
server.mjs          HTTP API、静态资源和数据导出
public/index.html   页面结构
public/app.js       交互、轮询和图表
public/style.css    桌面与手机样式
backend-check.mjs   关键业务边界验证
start.cmd           Windows 启动脚本
docs/               调研依据和课堂实验指南
```

`GET /api/state`、`GET /api/export`；`POST /api/start`、`POST /api/reset`；`POST /api/manual/query`、`claim`、`waitlist`、`confirm`、`cancel`、`refund`（后五项沿用同一个 `/api/manual/` 前缀）。

必要的业务验证可运行 `node backend-check.mjs`，覆盖库存守恒、身份去重、候补递补、退款回售、服务排队和轮次收尾。
