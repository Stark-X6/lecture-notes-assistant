# Ticket Lab · 抢票实验室

一个可交互的本地课程 Demo，包含售票服务、自动抢票程序、模拟手动群众、操作者手动抢票四个部分。所有参与者使用同一批库存和同一套业务分配逻辑。

## 启动

需要 Node.js 20 或更新版本，无需安装第三方包。

- Windows：双击 `start.cmd`，保持窗口运行。
- 命令行：在项目目录执行 `node server.mjs`。
- 浏览器访问 http://127.0.0.1:3186/ 。
- 关闭命令行窗口或按 Ctrl+C 停止。端口冲突时设置环境变量 PORT 使用其他端口。

当前电脑没有系统 Node 时，启动脚本会尝试使用已有的 Codex 内置 Node 运行时。代码也可以复制到装有 Node 的其他电脑运行。

## 建议体验顺序

1. 使用默认配置：30 张票、120 位群众、12 个抢票账号；选择「先到先得」，开始实验。
2. 开售后在绿色「操作者手动抢票」区域点击。拿到占位后，6 秒内点「确认订单」；也可取消，观察票额重新释放。
3. 等本轮结束，查看各组最终获票率与历史结果。
4. 保持参数相同，切换「限流去重」与「窗口抽签」再次开始。当前轮次运行中需先重置，未完成轮次不记入历史。
5. 抽签模式要在开售后指定窗口内点「登记抽签」；窗口结束后统一排序，中签者仍需确认。重复登记不增加机会。
6. 想轻松体验先点「载入练习配置」，它减少模拟参与者，不给操作者保留票。

支持调整票数、群众人数、自动账号数、倒计时、开售时长、程序重试间隔、共同上行延迟、波动、抽签窗口与随机种子。可筛选事件、导出 JSON 数据，并比较最近 10 个完整轮次。

## 模拟的具体含义

- 售票端是实际 Node HTTP 服务；操作者通过网页调用它。
- 群众和程序为后端进程内虚拟参与者，不会打开大量浏览器，也不会为每次虚拟请求创建真实 HTTP 网络连接。
- 三类参与者的占票请求都会进入相同 submit / FIFO / processClaim 流程。上行延迟在进入队列前模拟，业务处理耗时实际测量。
- 群众开售后约 300–2500ms 首次尝试，约 16% 的人还有额外迟到；重试等待约 900–2600ms，最多 6 次。程序开售后约 0–65ms 首次尝试，按配置重试。等待和网络完成后才安排后续重试。
- 模拟账号占位后约 350–1300ms 自动确认，约 3.5% 会取消。真人操作者需要手动确认；临近轮次结束的占位也必须在轮次结束前确认。
- 所有浏览器标签共用一个 `manual` 身份；这不是多人账号系统。
- 系统不会用 crowd / bot / manual 分组决定售票资格；分组用于安排参与行为和统计。模拟账号的确认行为与真人的手动确认行为不同。
- 只模拟上行延迟和波动，不完整模拟下行、带宽、丢包与互联网拥塞。页面约每 350ms 轮询状态，倒计时是根据服务端时间估算显示的。
- 固定种子只控制随机采样。系统调度与真人操作会改变时序，因此不保证同种子结果完全相同。
- 身份是假定有效且独立的，一个身份最多一张；不包含批量身份治理。
- 内存保存数据，服务重启后轮次和历史清空。重置保留本进程已完成的历史。
- 不连接 12306、大麦或任何真实票务服务，不涉及真实付款。

## 三种规则

| 模式 | 规则 | 观察重点 |
| --- | --- | --- |
| 先到先得 | 请求到达后按队列顺序竞争库存；始终保证一人一张 | 启动与反应时间带来的优势 |
| 限流去重 | 在基础规则上，同一身份至少间隔 800ms；重复提交不创建新占位 | 无效流量是否下降；首次提交优势可能仍在 |
| 窗口抽签 | 窗口内一身份一资格，关闭后均匀洗牌分配；释放后按候补递补 | 重复请求不增加资格，但迟到者被排除，等待增加 |

## 读懂指标

最终获票率 = 本组已确认账号数 / 本组参与账号数。

自动化优势倍数 = 程序最终获票率 / 群众最终获票率。群众成功率为 0 或无有效比较组时，界面显示「—」。临时占位和最终确认分别统计。

请求总数为已经到达业务处理路径的购票提交次数（不包含页面状态查询、确认和取消）。处理耗时为业务逻辑实际耗时，**不含**队列等待、模拟网络和页面轮询，不可当作端到端延迟。

单轮样本不能证明完全公平，尤其身份数量较少时。比较时保持票数、人数、时间和网络参数一致，运行若干轮观察波动。票额方块是当前归属的汇总视图，不是选座系统。

## 文件结构与接口

```
server.mjs          服务、虚拟参与者、分配机制、数据导出
public/index.html   界面结构
public/style.css    桌面与手机适配样式
public/app.js       交互、轮询、图表
backend-check.mjs   核心分配流程验证
start.cmd           Windows 启动脚本
```

接口：`GET /api/state`、`POST /api/start`、`POST /api/reset`、`POST /api/manual/claim`、`POST /api/manual/confirm`、`POST /api/manual/cancel`、`GET /api/export`。

检查核心流程：`node backend-check.mjs`。它使用本地独立服务实例，覆盖三种模式、库存守恒、重复提交、人工确认、过期释放和结束边界。

## 后续方向

当前版本适合展示业务规则对竞争结果的影响；它不是分布式压力测试平台。后续可把用户发生器拆成独立进程与真实 HTTP 请求，增加独立身份、数据库、分组网络参数、端到端耗时与多轮自动汇总。
