# 课堂实验指南

先用练习配置熟悉流程，再进行可比较的多轮实验。每轮结束后导出 JSON；同一比较中保持未研究的参数不变。重置会丢弃未完成轮次，不能把它当作已完成样本。

## 实验一：查询成功是否等于买到

设置少量票和足够竞争者，开售后由操作者查询。留意查询时间戳，再点击占票。如果其他请求已经完成占位，查询时有票、提交时无票是正常竞争结果。重复几轮观察，不保证每次都恰好出现这一时序。

记录查询时间、提交结果和当时库存。目的在于区分查询信息与库存预留，不是根据一次查询断言系统错误。

## 实验二：区分账号优势与人数优势

固定 6 位程序购票人，分别使用“6 账号、每人 1 账号”和“12 账号、每人 2 账号”，其他配置保持一致。程序成功率的分母都应为 6，避免将增加账号误当作增加了独立需求。

先比较先到先得，再比较行为防护。记录有效已确认票数、查询数、claim 数、每张有效票的请求成本、程序防护影响率和群众误伤比例。保护可能降低重复流量，首次反应优势仍可能存在。

## 实验三：库存如何回流

在练习配置下由操作者占票后取消，观察可售库存立即增加。重新开一轮，确认后退票，观察“已确认 → 待回售 → 可售”。若轮次先结束，待回售票可以留在池中，因为本轮已停止销售。

切换候补，增加竞争者并观察队列：取消或超时释放应优先递补；同人多个账号不会产生多份资格。手动取消候补后重新登记应排到队尾。窗口抽签采用随机顺序，与按登记时间递补的候补模式分开比较。

## 实验四：延迟不能全算网络问题

固定共同上行延迟和波动，分别运行较多服务通道与较少服务通道。也可保持通道数不变，提高模拟单次服务时间。观察队列深度、平均等待、P95 等待、端到端延迟和付款超时。

业务状态更新本身可能很快，但用户仍在等待网络、排队和服务定时器。付款也进入队列，忙时更可能错过占位期限。这是模拟服务容量变化，不是本机真实 HTTP 吞吐压测。

## 实验五：多轮比较规则

预先选定一组种子，例如 11、23、42、57、89，每种规则都运行这些种子，保留所有已完成结果。不要只保留防护效果最好的一轮。每组可先做 5 轮作为课堂探索，不能将小样本当作稳定结论。

推荐汇总：群众和程序有效获票率、两组优势倍数、claim 请求成本、群众受防护影响比例、等待和付款超时率。程序人数少时比率波动会很大；群众成功率为零时优势倍数没有有效分母。

固定种子不保证真人和系统调度可重放。若要减少真人带来的差异，比较轮次让操作者不参与，并如实写明。若所有需求都低于库存，结果也可能没有明显竞争，应保留这一解释。

## 报告建议

按“问题 → 固定条件 → 改变的参数 → 各轮结果 → 解释与限制”组织。截图配合 JSON 数据；写清账号数、独立人数、规则、种子、票数和服务参数。保护效果、群众体验和请求成本一起讨论，不以“最后防守方必胜”作为设计目标。
